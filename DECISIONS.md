# Design decisions

Key design decisions in burnrate, each with the reasoning and what it would cost if it turned out wrong.

## SLO model

- SLI queries are PromQL **series selectors** (`metric{matchers}`), not free-form PromQL or OpenSLO `metricSource` blocks — a selector is the largest language both an in-process matcher and `rate()` in Prometheus can evaluate identically, which is what makes the generated rules provably equivalent to the engine — users with SLIs that need joins, `histogram_quantile` or recording-rule inputs cannot express them; they would need a new indicator kind.
- the YAML is "OpenSLO-like" (`apiVersion/kind/metadata/spec`, `timeWindow`, `objectives`, `budgetingMethod`) with its own `apiVersion: burnrate/v1`, not OpenSLO v1 itself — OpenSLO's indicator shape is vendor-query based and could not carry the equivalence guarantee — OpenSLO files need light conversion before use.
- only `budgetingMethod: Occurrences`, rolling windows, and exactly one objective per SLO are accepted; anything else is a validation error, not silently ignored — the workbook's burn-rate alerting is defined on event ratios over rolling windows; Timeslices and calendar windows change the budget arithmetic — teams on calendar-month SLAs must approximate with a 30d rolling window.
- latency SLIs select the histogram bucket whose `le` equals the threshold (`le="0.25"`), with no interpolation between bounds; the threshold is validated as positive and finite, and `le` matchers in the histogram selector are rejected — neither the engine nor PromQL can count "requests under 300ms" exactly from buckets at 250ms/500ms, and interpolating would break equivalence — bucket bounds are only known at runtime, so a threshold that is not a bound selects no good series and the SLI reads 100% errors (loudly, every alert fires); the examples use 250ms, an OpenTelemetry default bound, and README Limitations calls this out.
- default alerting windows are stored as budget fractions (2%/1h, 5%/6h, 10%/1d, 10%/3d with short = long/12) and converted to burn rates per SLO period; a window pair may give `burnRate` or `budgetConsumed`, never both — the workbook derives 14.4/6/3/1 from budget fractions for 30 days, and keeping the fraction makes 7-day SLOs scale correctly — anyone expecting literal 14.4x on a 7d SLO sees 3.36x instead (the `validate` and `math` commands print the resolved numbers).
- a window pair whose threshold would need an error ratio above 100% is a validation error — such an alert can never fire, which is almost always a configuration mistake (e.g. 14.4x on a 90% SLO) — none expected.
- default budget policy is healthy ≥ 50%, warning ≥ 25%, critical > 0, exhausted ≤ 0; a custom policy's lowest state may have `minRemaining: 0`, meaning "anything above zero" — gives a usable default and lets `exhausted` always mean "overspent" — a team wanting a different default must write a `budgetPolicy` block.

## Engine semantics

- counter semantics follow Prometheus: per-series deltas, decreases are resets, the first sample of a series is a baseline — the engine must agree with `rate()` in the generated rules — the very first window after start-up undercounts by one sample per series, exactly as Prometheus does.
- exception to the baseline rule: a first sample counts in full when its OTLP start time is after the engine began observing, or when the same producer (resource + start time) already exported without that series — SDKs create the 5xx series on the first error; treating its first value as a baseline would hide the start of every outage — if a producer reuses a start time across restarts with different series, a few events could be double counted (not observed with real SDKs).
- series state evicted by `SeriesTTL` leaves a tombstone (metric + label key) on its producer, and a producer silent for `SeriesTTL` is retired with its tombstones instead of dropped, restored if the same producer + start time exports again, and forgotten after the longest SLO window; a tombstoned series that comes back is a baseline, overriding both first-sample exceptions — without it, an OTel asynchronous instrument that stops and resumes observing an attribute set (or a process partitioned for over an hour) re-delivers its lifetime count as new events and pages with zero new errors, which `rate()` would not — memory grows by one string per evicted series for the producer's lifetime plus one SLO period; errors that accrued while the series was not exported are not counted (in long windows `rate()` would count them across the gap), and a producer silent for longer than the longest SLO window whose stream started after the engine began observing is again counted in full on return.
- buckets are right-closed `(k·res, (k+1)·res]` and evaluation runs on resolution boundaries — a sample stamped exactly at `T` belongs to the evaluation at `T`, matching how Prometheus' range selectors include the end point — moving to left-closed would shift every expected transition by one step.
- alerts compare with strict `>` and no `for:` clause — the workbook's expressions use `>`; the long window already supplies the delay, and `for:` would break the closed-form detection times — burn exactly at threshold never fires (the `math` table shows "never" for e = B·(1−O)).
- error budget is computed over the events actually observed in the period window, not extrapolated to a full period — it is what `rate(x[30d])` does in Prometheus, so the two agree, and extrapolating would invent traffic — during the first period after deployment budgets swing hard (the demo shows −145% after one 12-minute outage in 4 days of data); documented in docs/ALERT_MATH.md §6.
- exhaustion ETA uses the burn rate of the shortest alerting long window (1h by default) — reacts within the hour without being as noisy as 5m — a slow, steady burn is projected from only the last hour.
- two evaluation clocks, `wall` (default, with a lateness allowance) and `data` (follow newest sample timestamp) — live use needs a ticker; replays and the demo need to run days of traffic in seconds — in `data` mode a single far-future timestamp advances the clock (only the wall clock rejects samples > 5m ahead).
- the ring uses blocks of 64 buckets with block sums recomputed from buckets on wrap — O(n/64 + 128) sums keep 30-day windows cheap at 1-minute resolution, and recomputation prevents float drift over long uptimes — memory is ~1 MB per 30-day SLO at 1m; much finer resolutions scale linearly.

## Rules generation

- one rule group per SLO; every window's ratio is computed from raw counters (`sum(rate(bad[W]))/sum(rate(total[W]))`), never by averaging shorter recording rules — Prometheus evaluates a group's rules in order in the same cycle, and averaging ratios weights quiet and busy periods equally — 30d `rate()` over raw counters is expensive on large Prometheus servers; a recording-rule cascade could be added as an opt-in.
- thresholds are emitted as `B * (1 - O)` rather than a precomputed decimal — PromQL then performs the same float64 operations as the engine, so ties break identically — slightly less readable rules.
- `prometheus/prometheus` is a **test-only** dependency (rulefmt, PromQL parser, TSDB, rule manager in the equivalence test); the shipped binary only uses `otlptranslator` and the OTLP protos — keeps the binary and its supply chain small while still validating against the real implementation — `go.mod` lists a large indirect dependency set.
- `promtool` validation is an opt-in target (`make promtool` builds it from the pinned module, `make promtool-check` runs `check rules` + `test rules`); `make check` uses Prometheus' rulefmt/PromQL packages in-process instead — `go install promtool@version` is refused (Prometheus' go.mod has replace directives) and building it needs network on first run, which `make check` must not — none for correctness: the in-process checks are the code promtool runs; CI runs both.
- equivalence tolerance between engine and Prometheus transitions is ±2 minutes — `rate()` extrapolates to window edges and ignores the first sample of lazily created series, so it can lead or lag exact bucket counts by a step or two — a real off-by-one regression smaller than 2 steps would not be caught by that test (the workbook tests pin the engine to the minute independently).

## Tooling and scope

- errcheck ignores `fmt.Fprint*` — report output goes through a tabwriter or buffer whose `Flush`/`Write` error is checked — a write error to a raw writer on a code path without a final check would be missed.
- coverage gate is 85% of statements per package measured by that package's own tests (`go test -coverprofile ./internal/...`), not cross-package `-coverpkg` (which reports a higher 96.6%) — the stricter number cannot be inflated by integration tests — none.
- synthetic traffic only; no real-world dataset — SLO alert timing needs ground truth that only a generator with exact incident boundaries provides — the tool has not been validated against real production traffic (stated in README Limitations).
- no state persistence across restarts in v1 — keeps the engine simple and the equivalence argument clean — after a restart burn rates and budgets rebuild from scratch (Prometheus rules have no such gap because the TSDB holds history; that is the recommended production path).
